## Cloud admin build-out (one zip per step)
- [x] Step 1 — Admin tree: /admin/cloud layout + 7 branch pages, shared guard/formatters, storage_settings + admin_action_log tables.
- [x] Step 2 — System settings (global max upload, plan quotas, extra-storage price, allowed file groups, storage maintenance mode). Pricing page and uploads now read them.
- [x] Step 3 — Quota engine. Per-user plan + extra storage + manual limits, freeze and ban, enforced on upload (maintenance → banned → frozen → per-file limit → free space; fails closed if the plan can't be verified). The storage service re-checks free space itself (`quota_bytes`). Admin can set all of it from /admin/cloud/users (look up by email or id, audited). Banned users also lose download/delete through the app.
- [x] Step 3b — Large uploads. Chunked, browser to storage service direct (8 MB chunks, resumable, SHA-256 checked per chunk). CoralzOne opens the session (quota, ban, freeze, free space) and finishes it (checks again), so a ban mid upload stops the file. The storage service reserves space for uploads in flight, refuses a wrong file type after the first chunk and finishes in the background. Needs the storage service redeployed and STORAGE_MAX_UPLOAD_MB set (4000 for Scale, needs Telegram Premium).
- [x] Step 4 — Buckets. Users create, rename and delete buckets at /cloud/buckets (Starter 1, Pro/Scale unlimited; unique names; delete only when empty) and pick one on the Storage page to filter files and upload into it. Admin: /admin/cloud/buckets (search by name or owner email, Frozen filter, owners over 80% full, paging) and /admin/cloud/buckets/{id} (owner, usage, newest files, freeze, delete with files). Freeze stops uploads into a bucket and checks again when a long upload finishes. Every change is in the admin log. No new migration (storage_buckets already existed). The Pricing page lists each plan's bucket limit. "Owner over 80% full" means strictly above 80%. A hiccup while finishing a big upload keeps the file and retries instead of cancelling it. Needs the storage service redeployed (two new routes).
- [x] Step 5 — Users & usage. /admin/cloud/users lists everyone (newest first) with search by name, email or full user id, filters for Frozen, Banned and plan (Starter includes people with no quota row), paging and each person's space, file count and bucket count. /admin/cloud/users/{id} is a read only overview: plan and flags, space used against the allowance, files, buckets (each links to its bucket page), space outside any bucket, newest files, API key totals and the last admin changes. /admin/cloud/users/{id}/controls holds the plan, extra storage, overrides, freeze and ban form from Step 3 (cap upload lives here). New gateway route GET /api/admin/cloud-users (admin only, read only, rate limited). The storage service's /buckets/usage now also returns each owner's file count; the page copes with the old service (counts show as unknown). Request totals and key reset need real API keys, so they arrive with Step 6: the page already shows key totals from storage_api_keys and says so when there are none. No migration. Needs the storage service redeployed for file counts only.
- [x] Step 6 — API keys (real, hashed). Keys are made on the server: 192 random bits, shown once, only the SHA-256 and the first 12 characters are stored (`cz_live_` + 4). The old /cloud/api-keys page kept fake keys in localStorage; it now uses the real thing and clears the old entry. Users: create (plan limit on ACTIVE keys: Starter 1, Pro 5, Scale unlimited; optional limit to one bucket), list, revoke at /cloud/api-keys. Deleting a bucket revokes keys limited to it, because the table's foreign key would otherwise turn them into all bucket keys. Public API, called with an `X-API-Key` header: GET /api/v1/files (newest first, limit, offset, bucket_id) and GET /api/v1/usage. Each call checks the key, its owner's ban, and a per key rate limit per minute (plan default Starter 60, Pro 300, Scale 1200, or an admin's custom value), then records last used and the request count. Wrong keys from one address are slowed after 30 a minute. Admin: /admin/cloud/api-keys (search name, prefix or owner email; Active and Revoked filters; paging), /admin/cloud/api-keys/{id} (owner, usage, set or clear a rate limit, revoke), the user overview lists that person's keys, and the user controls page can revoke all of their keys. Admins can never see or copy a key. Every admin change is in the admin log and in the person's history. NEEDS ONE MIGRATION: run /api/admin/migrate (or `bun run db:migrate`) once to add storage_api_keys.rate_limit_per_minute; it is safe to run again. Not built: upload, download and delete through the API (they must reuse the quota engine, so they are a later step), and monthly request or bandwidth caps (they need a usage ledger, planned with the Overview step). The docs page lists those as coming soon.
- [x] Step 7 — Files & abuse. /admin/cloud/files is now a real search over every file on the platform: name search (so `.zip` or `.exe` in a name works), a type picker, size presets (over 100 MB, 500 MB, 1 GB, 2 GB), sort (newest, oldest, largest, smallest), a Flagged filter, paging and the owner's email on each row. /admin/cloud/files/{id} shows one file (type, size, owner, bucket, flag) with: flag or clear a flag (optional reason), remove the file (confirm, deletes the bytes from Telegram first and keeps the row if Telegram is down so it can be retried), and block that file type. /admin/cloud/files/blocked-types lists every type the platform can store with its file count and a switch to block it; changes are staged and saved together. Blocked types are a normal audited setting (`blockedMimeTypes` in storage_settings, no migration needed) subtracted from the allowed list on every upload start, so blocking only stops NEW uploads; stored files stay until removed. Storage service: new admin routes (search, one file, per type counts, delete without owner id, flag) in app/api/storage/admin_files.py, plus `flagged_at` and `flag_reason` columns and size and type indexes added automatically at startup. Every admin file action goes through the gateway (PUT /api/admin/cloud-files), which writes the admin log; the old unaudited `adminDeleteStorageFile` server function was removed. Needs the storage service redeployed. Not built: scanning file contents for malware or illegal material (this platform only sniffs types from magic bytes), opening or previewing a file from the admin page (deliberately: reviewing a harmful file must not harm the admin), and `.exe` blocking by name (`.exe` files are already refused at upload because they are not an allowed type).
